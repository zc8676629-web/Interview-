# 简历分析 Demo 设计方案

日期：2026-08-21

## 1. 目标

先不做 Windows 桌面壳，先在当前项目里做一个“本地服务 + 本地网页”的真实可用 Demo。

第一版 Demo 必须完成以下闭环：

1. 上传本地简历文件。
2. 提取简历正文文本。
3. 调用 DeepSeek 真实模型接口。
4. 生成个人画像。
5. 生成可能的面试问题。
6. 在网页中展示结果。

目标不是做假流程，也不是做概念原型，而是做一个能真实使用、方便快速迭代的版本。

## 2. 范围

### 2.1 第一版包含

- 本地 Web 页面。
- 本地后端服务。
- 支持上传 `docx`、`pdf`、`txt` 简历。
- 提取简历纯文本。
- 通过 DeepSeek API 生成个人画像和面试问题。
- 页面展示原始文本摘要、个人画像、问题列表。
- 本地配置 DeepSeek API Key。
- 明确错误提示。

### 2.2 第一版不包含

- Electron 桌面打包。
- GitHub 发布流程。
- 多用户体系。
- 登录体系。
- 历史任务中心。
- 批量处理。
- 自动更新。
- 复杂模板管理。

## 3. 为什么先做服务 + 网页

相比一开始就做 Electron，这条路线更适合敏捷开发：

- 前后端改动更快。
- 接口调试更直接。
- 页面迭代成本更低。
- 后续如果要套 Electron，只需要在外层包一层桌面壳，不需要推翻现有服务和页面。

结论：第一阶段先把能力做成 Web Demo，第二阶段再视需要包成桌面应用。

## 4. 技术路线

建议采用：

- 前端：React + Vite
- 后端：Node.js + Express
- 文件上传：`multer`
- 文本提取：
  - `txt`：直接读取
  - `docx`：`mammoth`
  - `pdf`：PDF 文本提取库
- 模型接入：DeepSeek 官方 OpenAI 兼容接口

选择这条路线的原因：

- Node 前后端统一，开发和维护快。
- Vite 启动快，适合频繁改 UI。
- Express 足够支撑第一版 Demo。
- DeepSeek 当前官方接口兼容 OpenAI 风格，后端接入成本低。

## 5. DeepSeek 接入约束

当前设计基于 2026-08-21 当天核对的官方文档：

- OpenAI 格式 `base_url` 为 `https://api.deepseek.com`
- 当前主模型名使用 `deepseek-v4-flash` 或 `deepseek-v4-pro`
- 旧模型名 `deepseek-chat`、`deepseek-reasoner` 已在 2026-07-24 后退场，不应继续使用

第一版建议默认使用：

- `deepseek-v4-flash`

原因：

- 速度更适合 Demo 交互。
- 成本更可控。
- 后续可通过配置切换到 `deepseek-v4-pro`。

API Key 处理要求：

- 只保存在本地环境变量或本地 `.env` 文件。
- 不写死到源码。
- 不提交到 Git。

## 6. 用户流程

1. 用户打开本地网页。
2. 用户上传一份简历。
3. 前端将文件提交给本地服务。
4. 服务提取文本并做基础清洗。
5. 服务调用 DeepSeek 生成分析结果。
6. 前端展示：
   - 简历基础摘要
   - 个人画像
   - 可能的面试问题
7. 用户可以重新上传并再次分析。

## 7. 页面结构

第一版页面保持最小闭环，不追求复杂设计。

### 顶部

- 应用标题
- 当前状态提示

### 左侧区域

- 文件上传
- 当前文件信息
- 提取文本摘要

### 右侧区域

- 个人画像
- 面试问题列表

### 底部操作

- 开始分析
- 重新上传
- 复制结果

## 8. 后端模块划分

### 8.1 上传模块

职责：

- 接收文件上传。
- 校验文件类型和大小。

### 8.2 文本提取模块

职责：

- 针对不同文件类型提取正文。
- 输出统一纯文本。

### 8.3 文本预处理模块

职责：

- 清理空行、重复空白和明显噪音。
- 截断极端长文本，避免首版请求过重。

### 8.4 Prompt 组装模块

职责：

- 将简历文本包装成模型输入。
- 要求模型输出固定结构，便于前端展示。

### 8.5 DeepSeek 客户端模块

职责：

- 统一发起模型请求。
- 处理超时、接口异常和返回格式异常。

### 8.6 结果整形模块

职责：

- 将模型结果规范成前端固定 JSON 结构。

## 9. 接口设计

第一版只需要两个基础接口：

### `GET /api/health`

作用：

- 健康检查。
- 用于确认服务是否启动。

### `POST /api/analyze-resume`

作用：

- 接收简历文件。
- 返回分析结果。

返回结构建议包含：

- `fileName`
- `extractedTextPreview`
- `persona`
- `interviewQuestions`

其中：

- `persona` 为结构化文本或分段文本
- `interviewQuestions` 为字符串数组

## 10. 输出要求

### 10.1 个人画像

应重点覆盖：

- 候选人定位
- 技术栈概况
- 项目经验特征
- 业务经验特征
- 亮点
- 潜在追问点

### 10.2 面试问题

问题应尽量贴合简历原文，优先覆盖：

- 项目细节
- 技术实现
- 业务理解
- 角色职责
- 成果真实性
- 深挖追问

## 11. 错误处理

需要明确处理：

- 未上传文件
- 文件类型不支持
- 文件读取失败
- 文本提取失败
- DeepSeek API Key 未配置
- DeepSeek 请求失败
- 模型返回格式不符合预期

错误信息要求：

- 用户能看懂
- 能知道下一步怎么处理
- 不把底层异常直接甩给用户

## 12. 测试策略

第一版重点验证真实可用性。

### 必做验证

- `txt` 简历可完整跑通
- `docx` 简历可完整跑通
- `pdf` 简历可完整跑通
- API Key 未配置时有明确提示
- DeepSeek 请求成功时页面能正确展示
- DeepSeek 请求失败时页面能明确提示

## 13. 迭代策略

第一版只做最小闭环，后续再快速叠加：

1. 更好的解析和预处理
2. 更稳定的 Prompt
3. 问题分类展示
4. 导出 Markdown
5. 历史记录
6. Electron 外壳

## 14. 结论

当前最合适的起步方案是：

- 先做本地服务 + 本地网页
- 接 DeepSeek 真模型
- 做单份简历分析闭环
- 先保证真实可用
- 后续再快速迭代功能和体验

这个方案最符合“先做出可用 Demo，再敏捷迭代”的目标。
