# 简历画像与面试问题生成器 设计方案

日期：2026-08-21

## 1. 目标

构建一个基于 Windows 的 Electron 桌面应用，第一版聚焦本地简历分析。

应用需要完成三件核心事情：

1. 读取本地简历文件。
2. 根据简历内容生成个人画像。
3. 根据简历中体现的经历、技术和业务内容，生成可能在面试中被问到的问题。

第一版优先保证主链路可用、结构清晰、方便后续持续迭代，不追求一开始就做成重型平台。

## 2. 范围

### 2.1 第一版包含

- Windows 桌面应用。
- Electron 技术路线。
- 本地工具型应用，不依赖登录体系。
- 支持导入本地 `docx`、`pdf`、`txt` 简历。
- 提取简历正文文本。
- 对简历内容进行基础解析。
- 生成结构化个人画像。
- 生成可能的面试问题。
- 支持查看、复制、导出结果。

### 2.2 第一版不包含

- 多用户账号体系。
- 云端简历同步。
- 在线协作。
- 插件系统。
- 自动更新。
- 大规模批量任务中心。
- 复杂的模板市场。

这些能力后续可以加，但不进入第一版范围。

## 3. 用户流程

第一版的标准使用流程如下：

1. 用户打开应用。
2. 用户选择一份本地简历文件。
3. 应用完成文件校验和文本提取。
4. 应用展示解析出的基础信息和关键词。
5. 应用生成个人画像。
6. 应用生成可能的面试问题。
7. 用户查看结果，并选择复制或导出。

如果文件读取失败、文本为空或格式不支持，应用需要明确提示原因，并允许用户重新选择文件。

## 4. 设计方案对比

### 方案 A：规则优先

使用规则抽取固定字段，再用模板产出画像和问题。

优点：

- 结果稳定。
- 易于调试。
- 离线能力强。

缺点：

- 对简历写法变化的适应性弱。
- 输出容易僵硬。

### 方案 B：AI 优先

文本提取后主要依赖模型生成画像和问题。

优点：

- 对复杂简历的适应性更强。
- 输出更自然。

缺点：

- 结果波动更大。
- 可控性较弱。
- 更依赖模型能力。

### 方案 C：混合方案

先做规则解析，再基于解析结果生成画像和问题。

优点：

- 文件处理和字段抽取可控。
- 输出比纯规则更自然。
- 后续容易迭代和替换生成策略。

缺点：

- 设计上比单一路线多一层处理。

### 推荐结论

第一版采用方案 C，也就是“规则解析 + AI 生成”的混合方案。

这是当前最稳妥的路线，既能保证主链路可控，也能为后续优化问题质量保留空间。

## 5. 界面设计

第一版界面采用三栏主布局，加底部操作区。

### 左侧：简历导入区

- 选择文件按钮。
- 当前文件名显示。
- 文件类型和大小提示。
- 重新选择入口。

### 中间：简历解析结果区

- 提取状态。
- 基础信息摘要。
- 技能关键词。
- 项目经历或工作经历摘要。
- 业务方向标签。

### 右侧：生成结果区

- 个人画像。
- 可能面试问题。

### 底部：操作区

- 开始分析。
- 重新生成。
- 复制结果。
- 导出结果。

这个布局的目标是让用户同时看到输入内容、解析中间结果和最终产出，便于理解和校验。

## 6. 模块划分

### 6.1 文件导入模块

职责：

- 接收用户选择的文件。
- 校验扩展名和基础元信息。
- 将文件交给后续处理链路。

输入：

- 本地文件路径。

输出：

- 合法文件对象或错误信息。

### 6.2 文本提取模块

职责：

- 将 `docx`、`pdf`、`txt` 统一转成纯文本。
- 处理不同文件格式差异。

输入：

- 合法文件对象。

输出：

- 提取后的正文文本。
- 提取失败原因。

### 6.3 简历解析模块

职责：

- 从正文中提取结构化信息。
- 归纳岗位方向、技能、项目、公司、业务领域等内容。

输入：

- 正文文本。

输出：

- 结构化解析结果。

第一版建议抽取这些字段：

- 候选人基础信息。
- 目标岗位或岗位方向。
- 工作年限或经历阶段。
- 公司或项目经历。
- 技术关键词。
- 业务领域关键词。
- 简历中可直接支撑提问的亮点内容。

### 6.4 画像生成模块

职责：

- 根据结构化解析结果生成一份清晰、可读的个人画像。

输出应重点覆盖：

- 候选人的经验定位。
- 技术栈概况。
- 业务经验概况。
- 项目特征。
- 简历体现出的强项。
- 可能存在的薄弱点或追问点。

### 6.5 问题生成模块

职责：

- 根据简历内容生成可能的面试问题。

第一版问题生成优先围绕这些维度：

- 项目经历追问。
- 技术细节追问。
- 业务理解追问。
- 角色与职责追问。
- 成果真实性追问。
- 深挖型追问。

问题应尽量与简历原文有直接对应关系，避免泛泛而谈。

### 6.6 结果导出模块

职责：

- 支持复制结果。
- 支持导出分析结果到本地文件。

第一版导出格式可先支持纯文本或 Markdown。

### 6.7 本地配置模块

职责：

- 管理默认导出路径。
- 管理生成参数或模板配置。

第一版只保留最小配置能力，避免界面过重。

## 7. 数据流

主数据流如下：

1. 文件导入模块接收本地文件。
2. 文本提取模块输出纯文本。
3. 简历解析模块输出结构化结果。
4. 画像生成模块基于解析结果生成个人画像。
5. 问题生成模块基于解析结果生成面试问题。
6. 结果导出模块负责复制和落地导出。

解析结果是主中间层。

这样设计的原因是：

- 文件处理与生成逻辑解耦。
- 后续可以独立优化解析质量或生成质量。
- 新增文件格式时，不需要重做下游模块。

## 8. 错误处理

第一版至少需要覆盖以下异常：

- 不支持的文件格式。
- 文件不存在或无法读取。
- 文本提取失败。
- 提取结果为空。
- 解析结果不足以生成有效画像。
- 问题生成失败。
- 导出失败。

错误提示要求：

- 直接说明失败环节。
- 直接说明用户下一步该做什么。
- 不展示内部技术细节给普通用户。

## 9. 测试策略

第一版测试重点放在主链路稳定性上。

### 9.1 单元测试

- 文件格式判断。
- 文本提取结果标准化。
- 简历解析字段抽取。
- 画像生成输入输出约束。
- 问题生成输入输出约束。

### 9.2 集成测试

- `docx` 简历从导入到结果展示全链路。
- `pdf` 简历从导入到结果展示全链路。
- `txt` 简历从导入到结果展示全链路。
- 异常文件的错误提示流程。

### 9.3 手工验证

- Windows 上文件选择流程。
- 中文文件名兼容性。
- 结果复制与导出。
- 连续多次重新选择文件后的状态是否正确。

## 10. 仓库初始化建议

第一版仓库初始化应服务于后续持续迭代，不做一次性大而全的堆砌。

建议包含：

- Electron 主进程。
- 渲染进程前端界面。
- 本地处理服务层。
- 测试目录。
- 文档目录。
- 基础忽略规则。

不建议在第一天就加入过重的基础设施。

## 11. 后续演进方向

第一版完成后，后续可以按优先级逐步扩展：

1. 增加更多文件格式。
2. 增加问题分类和追问深度控制。
3. 增加多套画像模板和输出模板。
4. 增加批量处理。
5. 增加本地历史记录。
6. 增加自动更新和正式发布流程。

## 12. 结论

本项目第一版定位明确：

- 平台：Windows 桌面应用。
- 技术路线：Electron。
- 产品类型：本地工具型。
- 核心能力：读取本地简历，生成个人画像和可能的面试问题。
- 文件范围：`docx`、`pdf`、`txt`。
- 实现方式：规则解析 + AI 生成的混合方案。

这个方案已经足够支持下一步进入仓库初始化和实现规划阶段。
